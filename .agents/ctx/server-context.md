# Server Context

## Runtime Model

One Python codebase (`server/metis`), one Docker image, three logical processes (the worker runs as one container per queue). API records intent and streams; workers do all agent work; scheduler only enqueues.

| Process     | Entrypoint                 | Job                                                |
| ----------- | -------------------------- | -------------------------------------------------- |
| `api`       | `entrypoints/api.py`       | FastAPI REST `/v1`, SSE, auth                      |
| `worker`    | `entrypoints/worker.py`    | Arq jobs: `run_graph` (`jobs/run_graph.py`), `market_scan`, outbox relay; one process per queue (`AgentWorkerSettings`, `MaintenanceWorkerSettings`) |
| `scheduler` | `entrypoints/scheduler.py` | Market-watch ticks (15 min), nightly jobs          |

## Configuration

All config via env, loaded into `core/config.py` (pydantic-settings). No hardcoded values.

| Purpose          | Env var                                                   |
| ---------------- | --------------------------------------------------------- |
| Postgres         | `DATABASE_URL`                                            |
| Redis            | `REDIS_URL`                                               |
| Run lock         | `RUN_LOCK_TTL_SECONDS` (60), `RUN_LOCK_HEARTBEAT_SECONDS` (20; must be under half the TTL) |
| Stub specialists | `AGENT_STUB_SPECIALISTS` (false): true makes every specialist a stub (no LLM calls); set only for the web e2e stack, which has no LLM key |
| Sessions         | `SESSION_COOKIE_NAME` (default `metis_session`), `SESSION_TTL_DAYS` (30), `SESSION_IDLE_DAYS` (7; `1 ≤ idle ≤ ttl`), `COOKIE_DOMAIN` (optional), `COOKIE_SECURE` (optional; unset ⇒ `Secure` unless `APP_ENV=development`, read as `settings.secure_cookies`) |
| Google sign-in   | `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` (SecretStr), `GOOGLE_REDIRECT_URI`; all required unless `APP_ENV=development`, where unset ⇒ Google not offered (`settings.google_configured`) |
| LLM prices       | `LLM_PRICES` (optional JSON: model id → `{input_per_million_usd, output_per_million_usd}`; unset ⇒ no cost recorded, there is no built-in price list) |
| LLM embeddings   | `LLM_EMBEDDING_MODEL` (default `text-embedding-3-small`); called with the workspace's `llm` key and `base_url`; must return 1536-dimension vectors |
| Web app URL      | `WEB_BASE_URL` (default `http://localhost:3000`; sign-in redirects) |
| Key encryption   | `ENCRYPTION_MASTER_KEY`                                   |
| Web origin       | `CORS_ORIGINS` (comma-separated, e.g. `http://localhost:3000,http://localhost:8000`) |
| App DB role      | `APP_DB_PASSWORD` (read by migration `0004_app_role` only; gives `metis_app` LOGIN) |
| Tracing          | `LANGFUSE_*`, `OTEL_EXPORTER_OTLP_ENDPOINT`, `SENTRY_DSN` |

LLM and Exa keys are not env vars: they are per workspace (BYO), stored encrypted in `identity.provider_keys` (see Modules). `APP_ENV=development` is the only setting that allows an `http://localhost` (or `127.0.0.1`, `::1`) LLM `base_url`; everywhere else `base_url` must be https.

Secrets (`core/crypto.py`): envelope encryption with AES-256-GCM. `encrypt(plaintext, workspace_id) -> SealedSecret{ciphertext, nonce, wrapped_key, key_version}` seals each secret with its own random data key, wrapped by the master key for `key_version` (today only `1` = `ENCRYPTION_MASTER_KEY`). `workspace_id` is the AAD of both layers, so a secret cannot be opened in another workspace. `decrypt(sealed, workspace_id)` raises `SecretDecryptError` (`crypto.decrypt_failed`, 422: re-enter the key) on a wrong workspace, tampering or an unknown version. `mask(secret)` shows first 3 + `…` + last 4 for secrets of 12+ chars, else `…••••`. Never log or return plaintext.

## Ports

Core interfaces in `core/ports.py`. Adapters implement them; nothing else imports a vendor SDK.

| Port             | MVP adapter                                  | Used by                     |
| ---------------- | -------------------------------------------- | --------------------------- |
| `LLMProvider`    | OpenAI-compatible (`ChatOpenAI`, `base_url`) | agent graph, through `agent/llm.py` `LLMGateway` |
| `ResearchSource` | Exa hosted MCP server (`mcp.exa.ai/mcp`)     | Researcher, Scorer, Advisor |
| `OutputSink`     | Linear MCP, Markdown                         | Integrator                  |
| `InputChannel`   | Web (REST + SSE)                             | API                         |

Vendor adapters live in `metis/adapters/` and build on the shared plumbing in `metis/helpers/` (`httpx` and the `mcp` SDK; no vendor SDK):

- `helpers/http.py`: `provider_http_factory` (FastAPI dependency returning a `ClientFactory`: `make_client(headers) -> httpx.AsyncClient`, per-phase timeout, no redirects; adapters open one short-lived client per call; tests override it to route to fakes), `capped(provider)` (caps a whole call at `PROVIDER_TIMEOUT_SECONDS` = 10 s, else `timeout`) and `send(http, provider, request)`, which returns the JSON body or raises `UpstreamError` with `meta = {provider, reason}`, reason one of `unauthorized` (401/403), `unreachable`, `timeout`, `bad_response`, plus `rate_limited` and `server_error` from the LLM adapter (`FailureReason`). Keys, headers and upstream bodies never reach the error or logs.
- `adapters/llm/` (package; only it imports `langchain_openai` / `openai`, enforced by an import-linter contract): `client.OpenAICompatibleClient(make_client, base_url, api_key).list_models()` (`GET {base_url}/models`, spends no tokens; the SHIP-217 key test) and `chat.build_chat_model(base_url, api_key, model, purpose, callbacks, http_client)` → `OpenAICompatibleChat`, the `LLMProvider` over `ChatOpenAI` (`bind_tools`, `ainvoke` → `AIMessage`, `aclose`; 60 s call timeout, 2 retries). It takes decrypted credentials as arguments (an adapter imports no module). `purpose` picks the temperature (`interview` 0.7, `research` 0.3, `score` 0.0, `advise` 0.5, `spec`/`plan` 0.2, else 0.3). Every `openai` / `httpx` failure becomes `UpstreamError` (`provider.upstream_error`, `meta {provider: "llm", reason}`), reason `unauthorized` (401/403), `rate_limited` (429), `timeout`, `unreachable`, `server_error` (5xx) or `bad_response` (other statuses, malformed body); the key, prompts and upstream body are never in the error or logs.
- `core/ports.py`: `LLMProvider` protocol (`bind_tools(tools)`, `async ainvoke(messages, config) -> AIMessage`, `async aclose()`), using LangChain message types.
- `agent/llm.py`: `LLMGateway(workspace_id, run_id, sessions?, prices?, http_client?)`, one per run, the only way agent code gets a chat model. `await gateway.chat_model(session, purpose)` reads the key through `identity.get_key_for_use` (none → `ProviderNotConfiguredError`), builds the model once per `purpose` and caches it for the run; `await gateway.aclose()` at run end. A callback records every completed call through `ideas.record_llm_usage` in its own short transaction (so a failed run keeps its usage): provider-reported tokens (`0`/`0` when the reply has none) and `cost_usd` from `LLM_PRICES` (`null` without an entry). A failed usage write is logged (`llm.usage_record_failed`) and never fails the call. Only workers use it (invariant 1). `agent/tracing.py` adds the Langfuse callback only when `LANGFUSE_PUBLIC_KEY` and `LANGFUSE_SECRET_KEY` are set. Budget and step-limit enforcement is SHIP-237; this only records.
- `adapters/llm/embeddings.py`: `build_embedder(base_url, api_key, model, http_client)` → `OpenAICompatibleEmbedder` (the `Embedder`), one `POST {base_url}/embeddings` per call through the `openai` client (`encoding_format: float`, same timeout and retries as chat) → `EmbeddingBatch{vectors, input_tokens}`. A 404, or a 400 with code `model_not_found`, is `UpstreamError` reason `not_supported` (`FailureReason.NOT_SUPPORTED`); other failures map like chat.
- `core/ports.py` `Embedder` protocol (`model`, `async embed(texts) -> EmbeddingBatch`, `async aclose()`).
- `LLMGateway.embed(session, texts) -> list[list[float]] | None` (SHIP-229): uses `LLM_EMBEDDING_MODEL` on the workspace's `llm` key and `base_url` (no key → `ProviderNotConfiguredError`); records usage like a chat call (input tokens, output 0); returns `[]` for no texts. `not_supported`, or vectors that are not `research.EMBEDDING_DIMENSIONS` (1536) long, give `None`, log `llm.embeddings_unavailable` and turn embeddings off for the rest of the run; other `UpstreamError`s propagate. `aclose()` also closes the embedder.
- `helpers/pricing.py`: `ModelPrice`, `cost_usd(price, input_tokens, output_tokens)` (`None` without a price).
- `helpers/mcp.py`: `open_mcp_session(http, url, provider)` connects to a remote MCP server over streamable HTTP with a caller-built client (auth headers on the client), runs the handshake and yields a `ClientSession`; any failure becomes `UpstreamError` (`unauthorized` for HTTP 401/403, `timeout`, `unreachable`, else `bad_response`). Shared by every MCP-backed provider.
- `adapters/mcp/exa.py`: `ExaMcpClient(make_client, api_key).check()` calls Exa's hosted MCP server (`https://mcp.exa.ai/mcp`, key in `x-api-key`): one `web_search_exa` call with `numResults: 1` (`query` and `objective` are required). Exa also serves keyless searches, so only a tool call proves a key; a bad key comes back as a tool `isError` with `(401)` in its text → `unauthorized`. No `exa-py`.
- `adapters/mcp/oauth.py`: OAuth 2.1 for remote MCP servers with `httpx` only: `discover` (protected-resource metadata, RFC 9728, then authorization-server metadata, RFC 8414; every endpoint must be https, `localhost` only in development), `register_client` (dynamic registration, RFC 7591, public client when the server allows `none`), `authorization_url` (PKCE `S256`, `resource`), `exchange_code`, `refresh`, `revoke` (best effort). Tokens and the client secret are `SecretStr`; failures are `UpstreamError` with `meta {provider, reason}`, never carrying a code, token or body.
- `adapters/mcp/linear.py`: `LinearMcpClient(make_client, access_token).list_tools()` → `[ToolInfo{name, description}]` over `open_mcp_session` (`Authorization: Bearer`); `SERVER_URL = https://mcp.linear.app/mcp`. `adapters/mcp/client.py`: `build_mcp_client({name: McpServer(url, access_token)})` → `MultiServerMCPClient` (streamable HTTP, bearer header), the agent's tool loader (SHIP-233).

## Modules

`modules/<name>/` with `controller/` (HTTP routes), `service/` (business logic), `repo/` (all Postgres access, one file per table), `cache/` (all Redis key/value caches, one file per cache, when the module has any), `models/`, `dto/` (Pydantic data-transfer objects), `helpers/` (local, module-only), `events.py`; a layer is a folder with one file per domain when it covers several (see `code-standards.md`). Only `__init__.py` is public. Each module owns one Postgres schema.

| Module          | Owns                                             |
| --------------- | ------------------------------------------------ |
| `auth`          | users, sessions, sign-in identities, OAuth       |
| `identity`      | workspaces, members, provider keys, settings     |
| `ideas`         | ideas, interview turns, specs, workflow runs     |
| `research`      | snapshots, items, competitor KB, signals         |
| `scoring`       | score runs, params, suggestions, rubric versions |
| `planning`      | HLD, phases, tasks, task deps, plan diffs        |
| `integrations`  | MCP connections (OAuth), external refs, export jobs |
| `memory`        | memories (pgvector), guidance versions           |
| `notifications` | in-app notifications                             |

Import rules (import-linter, contracts in `server/pyproject.toml`, checked by `uv run lint-imports` in CI): `metis.core` and `metis.helpers` import nothing from `metis.modules`; `metis.modules.auth` imports no other module; `research`, `scoring` and `planning` (peers, none imports another) sit above `ideas`, which sits above `identity`, which sits above `auth`, in a layers contract, so `research | scoring → ideas → identity → auth` is allowed and the reverse fails; `research`, `scoring`, `planning`, `ideas` and `identity` may import only the public surface (`__init__.py`) of the modules below them (contracts in `server/pyproject.toml`). Identity imports only `metis.modules.auth` (its public surface: `router`, `current_user`, `CurrentUserDep`, `check_csrf`, `SessionUser`, `User`, `get_user`, `find_user_by_email`), never auth's `controller`, `service`, `models`, `repo`, `cache` or `dto`; a fourth import-linter contract ("identity uses only auth's public surface") fails CI on a direct import of any of them. `core/db.py` `insert_or_none(session, stmt)` (runs an `INSERT … RETURNING` in a savepoint, `None` on a unique conflict) is shared by both modules' `repo/` files.

Identity service contract (`modules/identity/service/`: `workspaces.py`, `members.py`, `provider_keys.py`, `settings.py`; the public functions are re-exported by `metis.modules.identity`): `ensure_personal_workspace(session, user)` (one `is_personal` workspace per user, race-safe), `list_workspaces(session, user)`, `create_workspace(session, user, name)`, `add_member(session, actor, workspace_id, email, role)` (owner only, else `PermissionDeniedError`; looks the email up with `auth.find_user_by_email`, unknown → `MemberUserNotFoundError`; existing member `AlreadyMemberError`). Every function takes the caller's `AsyncSession`, never commits (the caller owns the transaction) and sets its own RLS context (`app.user_id` / `app.workspace_id`, transaction-local), restoring the caller's value afterwards. Invalid input raises `InvalidInputError` (422) via `helpers.validation.validate_input`.

Identity provider keys and settings (same session rules): `get_settings_overview(session, workspace_id)` → masked keys + settings; `set_key(session, membership, kind, value, base_url?, model?)` seals the key with `crypto.encrypt` (workspace id as AAD), stores `sealed` (base64 `SealedSecret` fields, JSONB) and `masked`, upserts on `(workspace_id, kind)`, bumps `version` and clears the last test result; `delete_key(session, membership, kind)` (none → `ProviderKeyNotFoundError` 404); `test_key(session, workspace_id, kind, make_client)` makes one adapter call and records `last_tested_at`/`last_test_ok`, returning a `KeyTestResult` whose `error` is the `UpstreamError` (not raised, so the result commits); `get_key_for_use(session, workspace_id, kind)` → `ProviderCredentials{kind, api_key, base_url, model}` (none → `ProviderNotConfiguredError`), callable only by the LLM gateway and the Exa adapter; `update_settings(session, membership, patch)` with optimistic concurrency (`version` 0 = never saved: creates the row; stale → `ConflictError` 409). Writes (`set_key`, `delete_key`, `update_settings`) are owners only (`PermissionDeniedError` 403); any member reads and tests. Settings: `run_budget_usd` default 2.00, `0 < x ≤ 100`, 2 decimals; `max_steps` default 50, `1 ≤ x ≤ 200`; no row means defaults (`version` 0). Both tables have RLS.

Identity routes (`modules/identity/controller/`: `workspaces.py`, `settings.py`): `GET /v1/workspaces/current` → `{workspace, role}` (the request's current workspace, `X-Workspace-Id` or the personal one; the first call creates the personal workspace); `GET /v1/workspaces` → `{items: [{workspace, role}], next_cursor: null}`; `POST /v1/workspaces` `{name}` → `201 {workspace, role: "owner"}`; `GET /v1/settings` → `{keys: {llm, exa}, settings: {run_budget_usd, max_steps, version}}` (a key is `{kind, base_url, model, masked, last_tested_at, last_test_ok, version, updated_at}` or `null`); `PATCH /v1/settings` `{version, run_budget_usd?, max_steps?}` → settings or 409; `PUT /v1/settings/keys/{kind}` `{value, base_url?, model?}` → key; `DELETE /v1/settings/keys/{kind}` → 204; `POST /v1/settings/keys/{kind}/test` → key (ok) or 502 `provider.upstream_error` with `meta {provider, reason}`. No response ever contains a plaintext key.

Ideas (`modules/ideas/`, `ideas` schema, migrations `0010_ideas`, `0011_llm_usage`, `0013_workflow_runs`, `0014_run_active_index`, `0015_interview_turns`, `0020_spec_versions`; public surface `router`, `Idea`, `IdeaKind`, `NewLlmUsage`, the interview names below, `RunKind`, `RunRef`, `RunStarted`, `RunStatus`, `Stage`, `WorkflowRun`, `create_run`, `start_refresh_run`, `get_idea`, `get_run`, `list_running_runs`, `mark_awaiting_user`, `mark_cancelled`, `mark_failed`, `mark_running`, `mark_succeeded`, `record_llm_usage`, `set_current_score`, `transition`, `apply_revision`, `AdviceDecision`, `AdviceResume`, the spec names under Specs below): table `ideas.llm_usage` (migration `0011_llm_usage`: `id`, `run_id` (FK to `ideas.workflow_runs` since `0013`, cascade), `workspace_id`, `model`, `input_tokens`, `output_tokens`, `cost_usd numeric(12,6)` null, `created_at`; RLS; index `(workspace_id, run_id)`; written by `service.llm_usage.record_llm_usage(session, workspace_id, NewLlmUsage)`, which never commits) and table `ideas.ideas` (`id`, `workspace_id`, `created_by`, `title`, `raw_text`, `kind` software|other|null, `stage`, `current_score` 0–100|null, `version`, `archived_at`, `created_at`, `updated_at`; RLS; `interview_brief` jsonb|null (since `0015`); `kind`/`stage` text + CHECK). Service functions (`modules/ideas/service/ideas.py`, caller's session, never commit, scoped to the workspace id as well as RLS): `create_idea(session, user, membership, NewIdea)` (stage `intake`, version 1, adds an `IdeaSubmitted` outbox event `{idea_id, created_by}` in the same transaction), `get_idea(session, workspace_id, idea_id)`, `list_ideas(session, workspace_id, cursor, limit, q, filter)` (latest activity first, keyset on `(updated_at, id)` with index `ix_ideas_workspace_activity` (`0022`), opaque base64url cursor, default 20, max 100, archived hidden; `q` = case-insensitive literal title substring, ≤ 100 characters, blank means none; `filter` = `all` | `in_progress` (stages before `spec_confirmed`) | `scored` (`current_score` set)); `updated_at` is last activity: it moves on edit, archive, every stage move, `set_current_score` and run start (`create_run`, `start_run`, refresh runs), the last two without a `version` bump; `live_idea_ids(session, workspace_id, ids)` (public: the unarchived ids among `ids`), `update_idea(session, user, membership, idea_id, IdeaPatch)` (title/raw_text/kind; stale `version` → `ConflictError` 409; bumps `version`), `archive_idea(...)` (sets `archived_at`; archived ideas are `idea.not_found` everywhere), `transition(session, workspace_id, idea_id, to_stage)` (checked against `helpers/transitions.ALLOWED_TRANSITIONS`, else `IllegalTransition` 409 `idea.invalid_transition`; bumps `version`; no HTTP route yet). Edit and archive: the idea's creator or a workspace owner, else `IdeaNotOwnerError` (`idea.not_owner`, 403); every member reads. Validation (trimmed first): title 3–120, raw text 10–10,000 characters. Transition table: `intake → interviewing → researching → scoring → advising | spec_draft`; `advising → interviewing | researching | scoring | spec_draft`; `spec_draft → spec_confirmed`; `spec_confirmed → spec_draft | planning`; `planning → exported`; `exported → planning`. Routes (`/v1/ideas`, all on `current_workspace`): `POST` `{title, raw_text, kind?}` → 201 idea; `GET ?cursor=&limit=&q=&filter=` → `{items, next_cursor}` (ordered by `updated_at`); `GET /{id}`; `PATCH /{id}` `{version, title?, raw_text?, kind?}` (`kind: null` clears it); `DELETE /{id}` → 204 (archive); `GET /{id}/interview` → `{items: InterviewTurn[]}`, the idea's interview turns across all runs, oldest first (uuid7 id), each `{id, idea_id, run_id, topic, source: asked|noted, question, answer|null}`, `[]` when none, unknown/archived/foreign idea → `idea.not_found` (`service.interview.list_interview`). An idea body is `{id, workspace_id, created_by, title, raw_text, kind, stage, current_score, version, created_at, updated_at}`.

Workflow runs (SHIP-228, `service/workflow_runs.py`, `repo/workflow_runs.py`, `helpers/run_transitions.py`): table `ideas.workflow_runs` (migration `0013_workflow_runs`: `id`, `workspace_id`, `idea_id` (FK, cascade), `kind` (`pipeline` by default; `rescore` and `market_recheck` added by migration `0018_manual_refresh_runs`, text + CHECK), `status` (text + CHECK over `RunStatus`), `started_at`, `finished_at`, `error` jsonb `{code, message}`, `pending_interrupt` jsonb, `idempotency_key` (unique per workspace), `version`, timestamps; RLS; index `(workspace_id, status)`). Status table: `queued → running | cancelled`; `running → awaiting_user | succeeded | failed | cancelled`; `awaiting_user → running | cancelled`; terminal statuses have no exits (`IllegalRunTransition`, `run.invalid_state`, 409). Service (caller's session, never commits, scoped by workspace id as well as RLS): `create_run(session, workspace_id, idea_id, idempotency_key=None)` (a `queued` run; unknown idea → `IdeaNotFoundError`), `get_run` (`RunNotFoundError`, `run.not_found`, 404), `mark_running` (a run already `running` is returned unchanged; sets `started_at` once, clears `pending_interrupt`), `mark_awaiting_user(…, pending_interrupt)`, `mark_succeeded`, `mark_failed(…, error)`, `mark_cancelled`; a lost race re-reads the row. `list_running_runs(session)` returns `RunRef{run_id, workspace_id}` for every `running` run in any workspace through the `SECURITY DEFINER` function `ideas.list_running_runs()` (executable by `metis_app` only; the owner role must bypass RLS); only crash recovery calls it. The one-active-run-per-idea rule, idempotent start and the HTTP routes are in the Runs API below (SHIP-232).

Interview (SHIP-236, `service/interview.py`, `repo/interview.py`, `dto/interview.py`): table `ideas.interview_turns` (migration `0015_interview_turns`: `id` (uuid7; turns are ordered by it), `workspace_id`, `idea_id` (FK, cascade), `run_id` (FK `workflow_runs`, cascade), `topic` (`InterviewTopic`: `problem`, `solution`, `customer`, `payment`, `feasibility`, `other`; text + CHECK), `source` (`asked` | `noted`), `question`, `answer` (null while an asked question waits), `created_at`; RLS; partial unique index `uq_interview_turns_open_question` on `(run_id) WHERE source = 'asked' AND answer IS NULL`). The checklist is the first five topics (`CHECKLIST`); "current alternatives" is part of `solution`. A topic is covered by a turn whose answer is not empty, not `skip` and not a stop phrase (`STOP_ANSWERS`: "that's enough", "thats enough", "enough", "stop"; compared casefolded without end punctuation). Runs API (SHIP-232, `modules/ideas/controller/runs.py`; all routes on `current_workspace`, mutations need `X-Metis-Client: web`; any workspace member may call them). The API records intent and queues the job; it never runs the graph. Handlers commit first and enqueue second (the services never commit), so a worker never looks for a run that is not saved:
  - `POST /v1/ideas/{idea_id}/runs` (header `Idempotency-Key`, required, 1–255 printable ASCII; no body) → `202 {run_id}`. `service.start_run`: unknown/archived/foreign idea → `idea.not_found`; the key already used → that run (on another idea → `409 run.idempotency_mismatch`); an idea with a `queued`, `running` or `awaiting_user` run → `409 run.already_running`; else a `queued` run and `run_graph(run_id=<str>, workspace_id=<str>)` with `job_id=run_id`. Partial unique index `uq_workflow_runs_active_idea` on `workflow_runs (idea_id)` for those three statuses (migration `0014`) makes the rule hold under a race; the same key racing resolves through `(workspace_id, idempotency_key)`. A retry of a still-`queued` run enqueues again with the same job id (Arq dedupes), which repairs a commit whose enqueue failed. An enqueue error → `503 run.enqueue_failed`; the `queued` row stays.
- `POST /v1/ideas/{idea_id}/rescore` and `POST /v1/ideas/{idea_id}/recheck-market` (SHIP-242; required `Idempotency-Key`, no body) → `202 {run_id}`. Refresh graphs start at `scoring` or `researching`, never write their working stage back to `ideas.stage`, and end after scoring without running Advisor or Architect. If Exa is unavailable during re-check, score with an explicit no-fresh-research seed and omit all older research evidence.
  - `POST /v1/runs/{run_id}/resume` `{value}` → `202 {run_id}`. Only `awaiting_user` (else `409 run.invalid_state`). `value` is checked against `pending_interrupt.type` (`helpers/resume_value.py`): `question` → text (trimmed, 1–10,000 characters) or `{option_ids?, text?}` (below); `approval` → a boolean; `spec_review` → always 422 (the confirm route answers it); `phase_review` → an object `{phases: [{name, goal, exit_criteria}]}` (1–12 phases; name 1–120, goal and exit criteria 1–1,000 characters, trimmed; no other fields; approving as is means sending the proposed list back); `advice_decision` → an object `{decision: revise|continue|stop, revised_text?, accepted_suggestion_ids?}` (`revise` needs `revised_text` of 10–10,000 characters; up to 5 UUIDs; no other fields); a value of another shape for the pending interrupt, or any other interrupt type → 422. Enqueues `run_graph(..., resume=value)` with `job_id={run_id}:resume:{run.version}` (the version moves on every status change, so one pause queues once and a later pause gets a new id). The row is not changed; the worker moves it to `running`.
  - `POST /v1/runs/{run_id}/cancel` → `202 {run_id, status}`. `queued`/`awaiting_user` → `cancelled` in the same transaction, then `cancel:{run_id}` (TTL 24 h) is set and `run_status: cancelled` is published; `running` → only the flag is set, status stays `running` and the worker ends it at the next step; already `cancelled` → 202 `cancelled`; `succeeded`/`failed` → `409 run.invalid_state` and no flag.
  - `GET /v1/runs/{run_id}` → `RunView {id, idea_id, kind, status, stage, pending_interrupt, error, started_at, finished_at, created_at, version}`; `stage` is the idea's current stage read live; `workspace_id` and `idempotency_key` are not exposed; a run of an archived idea is `404`.
  - `GET /v1/ideas/{idea_id}/runs?cursor&limit` → `{items: RunView[], next_cursor}`, newest first, keyset on `(created_at, id)`, default 20, max 100.

  - Routes (`/v1/integrations`): `GET` → `{items: [{provider, status: not_connected|connected|expired, scopes, expires_at, connected_at, connected_by, version}]}`; `POST /{provider}/connect` `{redirect_to?}` → `{authorize_url}` (`redirect_to` is a same-site path, default `/?settings=integrations`); `GET /{provider}/callback?code=&state=&error=` (session cookie, no workspace header; commits only on success; answers `302` to `WEB_BASE_URL + redirect_to` with `integration=<provider>`, or to `/?settings=integrations&integration_error=<code>` on any failure, or to `/sign-in` without a session); `GET /{provider}/tools` → `{items: [{name, description}]}` (409 `mcp.not_connected` / `mcp.expired`); `DELETE /{provider}` → 204.

## Auth and Request Scope

- Auth is the session cookie only (SHIP-267 removed JWT bearer auth, `core/auth.py` and `AUTH_JWT_*`). An `Authorization` header is ignored. PyJWT is imported only by `modules/auth/providers/google.py` (Google `id_token`s).
- `core/db.py`: `SessionDep` = one `AsyncSession` per request (`get_request_session`, `scope="function"`), shared by every dependency and the route; committed before the response is sent, rolled back on any exception. `set_workspace(session, id)` / `set_user(session, id)` set `app.workspace_id` / `app.user_id` for the transaction.
- `modules/auth/deps.py` (exported from `metis.modules.auth`): `current_user` (`CurrentUserDep`) → `SessionUser{user, session_id}` (frozen, in `auth/dto/sessions.py`). Checks in order: no cookie → `NotSignedInError` (`auth.not_signed_in`, 401); `POST`/`PUT`/`PATCH`/`DELETE` without `X-Metis-Client: web` → `CsrfError` (`auth.csrf_failed`, 403); then the session must resolve (`auth.session_expired`, 401). Binds `user_id` and `session_id` to logs. 401s carry no `WWW-Authenticate` header.
- `modules/identity/deps.py` (exported from `metis.modules.identity`): `current_workspace` (`CurrentWorkspaceDep`, built on `auth.CurrentUserDep`) reads `X-Workspace-Id` (absent → personal workspace, created by `ensure_personal_workspace` if missing; not a UUID → 422; not a member or unknown → `PermissionDeniedError` 403, same error for both), then sets `app.user_id` and `app.workspace_id` on the request session and binds `workspace_id`/`user_id` to logs. Returns the caller's `Membership`.
- Every `/v1` route except `/v1/health` and the public `/v1/auth/*` routes (`providers`, `google/login`, `google/callback`, `logout`) depends on `current_user` or `current_workspace`; tenant routes use `current_workspace` so RLS is scoped. `tests/modules/auth/test_route_auth.py` walks the route table and fails on any other route that answers without a session.
- **Server sessions (SHIP-264):**
  - `core/security.py`: `new_session_token()` (32 random bytes, URL-safe), `hash_session_token(token)` (SHA-256 digest; only the hash is stored), `set_session_cookie(response, token)` / `clear_session_cookie(response)` (`SESSION_COOKIE_NAME`, `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` = `settings.secure_cookies`, `Domain` = `COOKIE_DOMAIN` when set, `Max-Age` = `SESSION_TTL_DAYS`).
  - `core/redis.py`: one process-wide Redis client (`get_redis` / `RedisDep`, 0.5 s socket timeouts), closed in the API lifespan.
  - Tables `auth.users`, `auth.identities` (`user_id`, `provider` ∈ `google`, `email`, `subject`, `email`, `email_verified`, `last_login_at`; unique `(provider, subject)`) and `auth.sessions` (`token_hash` unique, `last_seen_at`, `expires_at`, `revoked_at`, `user_agent`, `ip inet`); sessions and identities cascade on user delete. No RLS; only the auth module reads them. `identity.workspaces.created_by` and `identity.members.user_id` reference `auth.users`. `0006_auth_sessions` backfilled one `google` identity per existing user from `users.auth_sub`; `0007_drop_users_auth_sub` dropped that column; `0008_auth_schema` moved all three tables from `identity` to `auth` (`SET SCHEMA`, no data copied). `0009_rename_auth_identities` renamed `auth.auth_identities` to `auth.identities` (with its `pk_`/`fk_`/`uq_`/`ck_` constraints and `ix_identities_user_id`); model `IdentityRow`.
  - `modules/auth/service/` (`sessions.py`, `users.py`, `identities.py`, `oauth.py`, called domain-qualified, e.g. `service.sessions.create_session`; caller's session, never commits): `create_session(session, user_id, user_agent, ip) -> NewSession{token, session_id, expires_at}`; `resolve_session(session, redis, token) -> ActiveSession` (unknown, revoked, `now ≥ expires_at` or idle `≥ SESSION_IDLE_DAYS` → `SessionExpiredError`; writes `last_seen_at` at most every 5 min); `logout(session, redis, token)` (no-op if unknown); `logout_all(session, redis, user_id) -> count`; `get_session_user(session, active) -> SessionUser`; `get_user(session, user_id) -> User | None` and `find_user_by_email(session, email) -> User | None` (email trimmed, case-insensitive, as `add_member` does). Only `get_user` and `find_user_by_email` are exported; the rest is internal to auth (its routes, `deps.py` and tests).
  - Session cache (`modules/auth/cache/sessions.py`: `read`, `write`, `mark_revoked`): Redis `auth:session:{hex hash}` → `SessionRecord` JSON, TTL `min(60 s, until expires_at)`, active sessions only. Revoking writes a tombstone `auth:session:revoked:{hex hash}` (120 s, longer than any entry) and deletes the entry; readers check the tombstone first, so a request that read the session before the revocation committed cannot re-cache it, and revocation applies on the next request. A rolled-back logout leaves the session refused until the tombstone expires. If Redis is down at logout, a cached entry stays valid for up to 60 s (`auth.session_cache_evict_failed`). Other Redis errors are logged (`auth.session_cache_unavailable`) and fall back to Postgres.
  - Never log the raw token, `Cookie` or `Set-Cookie`. Rejections log `auth.session_rejected` with `reason` ∈ `missing`, `unknown`, `expired`, `idle`, `revoked`, `csrf` (plus `session_id` when known).
- **Google sign-in (SHIP-265):**
  - Providers (`modules/auth/providers/`): `AuthProvider` protocol (`name`, `async authorization_url(state, nonce, code_challenge)`, `async complete(code, code_verifier, nonce) -> ProviderProfile{provider, subject, email, email_verified, name, avatar_url}`), `AuthProviderName` (`google`, `email`; matches the `auth.identities.provider` CHECK). `GoogleProvider` uses only `httpx` + PyJWT: discovery document and JWKS cached 1 h per instance; an unknown `kid` refetches the JWKS at most once a minute; `id_token` checked `RS256` only, signature, `iss` ∈ {`https://accounts.google.com`, `accounts.google.com`}, `aud = GOOGLE_CLIENT_ID`, `exp`/`iat`/`sub` required (30 s leeway), then `nonce` (constant-time). Scopes `openid email profile`, `prompt=select_account`. `get_google_provider` / `GoogleProviderDep` → one process-wide instance or `None` when not configured (tests override it). Every failure is `OAuthFailedError`, logged `auth.oauth_failed` with `provider`, `step` (`OAuthStep`) and `reason` (`OAuthFailure`).
  - `core/security.py`: `new_oauth_value()` (state / nonce, 32 random bytes), `new_code_verifier()`, `code_challenge(verifier)` (PKCE `S256`). `helpers/redirects.py`: `safe_relative_path(value)` keeps only a same-site relative path (starts with one `/`, no scheme/host, no backslash or control characters, ≤ 2048 chars), else `/`.
  - `auth.service.identities.sign_in(session, profile) -> SignedIn{user, outcome}`: unverified email → `EmailUnverifiedError` (always, even for a known identity); `(provider, subject)` match → `existing`; else a user with the same email gets the identity linked → `linked`; else a new user → `created` (no personal workspace; see `current_workspace`). A malformed profile (bad email, non-HTTP image, overlong name) → `auth.oauth_failed`. Sets `last_login_at` and refreshes the identity's email. A unique-constraint race retries once (savepoints), then `auth.oauth_failed` (`sign_in_conflict`). Logs `auth.sign_in` (`provider`, `outcome`, `user_id`).
  - OAuth round trip (`modules/auth/service/oauth.py`): `start_login(redis, provider, redirect_to)` stores `PendingLogin{nonce, code_verifier, redirect_to}` at Redis `auth:oauth:{state}` (600 s, `cache/oauth.py` `save_pending`) and returns the provider URL; `finish_login(...)` takes it back with `GETDEL` (`take_pending`; single use; missing/unknown/expired/corrupt → `OAuthStateInvalidError`), then provider `error=` / missing code → `auth.oauth_failed`, `provider.complete`, `sign_in`, `create_session`. Redis down at login or callback → `auth.oauth_failed`.
  - Routes (`modules/auth/controller/`: `providers.py`, `google.py`, `sessions.py`; `/v1/auth`, public): `GET /providers` → `["google"]` (or `[]`); `GET /me` → the signed-in `User` (session cookie required; touches no workspace); `GET /google/login?redirect_to=` → 302 to Google; `GET /google/callback` → commit, set the session cookie, 302 to `WEB_BASE_URL + redirect_to`; any failure → rollback, no cookie, 302 to `{WEB_BASE_URL}/sign-in?error=<code>`. `POST /logout` → CSRF check (`check_csrf`), revoke the cookie's session if any, clear the cookie, 204 (idempotent). `POST /logout-all` → `CurrentUserDep` (401 without a session), revoke all the user's sessions, clear the cookie, 204.
  - Never logged: the code, `code_verifier`, `state`, `nonce`, tokens, `id_token`, the client secret. `core/logging.py` installs `StripQueryFilter` on `uvicorn.access`, so access lines carry the path without its query string (the callback's `code` and `state` live there).
  - Sign-in writes (`sign_in` + `create_session`) run in a savepoint inside `finish_login`, and each `sign_in` attempt in its own, so a failed callback or a lost race leaves no user, identity or session behind.
- CORS: only `CORS_ORIGINS` (`*` fails settings validation), credentials allowed (session cookie), headers `Content-Type`, `X-Workspace-Id`, `Idempotency-Key`, `X-Request-ID`, `X-Metis-Client`.
- DB roles: api and workers connect as `metis_app` (`NOSUPERUSER NOBYPASSRLS`, DML on `core`, `identity`, `auth` and `ideas` + default privileges; `auth` granted by `0008_auth_schema`, `ideas` by `0010_ideas`, the schema itself being created by `0001_initial`); migrations run as the owner. A migration adding a schema grants `metis_app` on it.

| ----------- | --------------------------------------------------------------------------------------------------------------- |
| Supervisor  | none; routes on `MetisState.stage`                                                                              |
| Interviewer | `ask_user`, `recall_memory`, `save_interview_turn`, `finish_interview`                                          |
| Researcher  | Exa MCP (`web_search_exa`, `web_fetch_exa`), `kb_lookup`, `kb_upsert_competitor`, `save_research_item`          |

- `ask_user(question)` and `request_approval(action, details)` (`agent/tools/ask_user.py`) call `interrupt()` with `{"type": "question", "question"}` / `{"type": "approval", "action", "details"}`; resume with `Command(resume=value)` (an answer string, or a boolean for approvals). The Advisor's node calls `interrupt({"type": "advice_decision", score_run_id, total, band, suggestion_ids})` itself and resumes with an `AdviceResume` dict. A node that calls them is re-run from its start on resume, so it does nothing with side effects first. The Planner's `propose_phases` calls `interrupt({"type": "phase_review", "phases": [{name, goal, exit_criteria}]})` and resumes a `PhaseReviewResume` dict.
- State holds ids and summaries only. The runner streams it as described under "Running a run".
- `MetisState` (`agent/state.py`): `run_id`, `workspace_id`, `idea_id` (strings), `stage`, `messages` (`add_messages`), `summary`, `step_count`, `budget` (`{max_steps}`), `pending_approval`, `last_error`, `clarification`, `clarification_rounds`, `research_skipped`. `initial_state(...)` builds a run's start. A checkpoint restores `stage` as a plain string, so compare with `==`, never `is`.
- Supervisor (`agent/supervisor.py`): pure. `STAGE_ROUTES` maps every `Stage` to a specialist (`intake`/`interviewing` → Interviewer, `researching` → Researcher, `scoring` → Scorer, `advising` → Advisor, `spec_draft` → Architect, `spec_confirmed` → Planner, `planning` → Integrator, `exported` → end). `supervise` sets `last_error = run.step_limit_reached` when `step_count >= budget.max_steps`; `route` ends the run on `last_error`, `exported` or `research_skipped`. The caller (the `run_graph` job, SHIP-225) loads `max_steps` from workspace settings and passes it in `budget`.
- Graph (`agent/graph.py`): `build_graph(checkpointer, specialists=None)` compiles START → supervisor → specialist → supervisor. `specialists` replaces stub nodes by `Specialist`. Stubs (`agent/specialists/stubs.py`) advance the stage and emit a custom `node_finished` event `{type, node}`; a stub run visits every specialist: `intake → interviewing → researching → scoring → advising → scoring → spec_draft → spec_confirmed → planning → exported` (the stub Advisor loops back to `scoring` once, leaving `ADVISED_MARKER` in `summary`).
- Interviewer (SHIP-236, `agent/specialists/interviewer.py`, tools in `agent/tools/interview.py`, prompt `interviewer.v3.md`): at `intake` it only moves the run to `interviewing` (no model call). At `interviewing` it runs `build_react_specialist` (step limit 40 between two pauses; each resume counts again; `finish_tools={finish_interview}` ends the loop) over the `interview` chat model, seeded with the idea's title and text, then stores the brief (`ideas.finish_interview`) and moves the run to `researching`; the runner saves the stage (see "Running a run"). Hitting the step limit ends the run with `run.step_limit_reached`. Tools, each bound to one run and opening its own short transaction: `ask_user(question, topic, options?, multi?, allow_free_text?)` (SHIP-294) saves the question (`ideas.open_question`), calls `interrupt(payload)` and saves the answer; the payload is `{type: "question", question, multi, options: [{id, label, detail?, recommended}], allow_free_text, index, total}` (`agent/tools/question_options.py`). Options: 2–5, label 1–80 characters, detail ≤ 160, labels unique (casefolded), at most one `recommended` unless `multi`; ids `o1`, `o2`, … are assigned by position by the tool, not the model; a proposal that breaks a rule comes back as a message and opens no turn. No options → `options: []`, `multi: false`, `allow_free_text: true`. `index` is the run's asked-question count including this one; `total` = `min(8, index + checklist topics still missing, not skipped and not this one)` (`ideas.question_progress`), an estimate that never falls below `index`. The Researcher's clarification question stays `{type, question}` (no options, no `index`/`total`). Resume: `check_resume_value` turns `{option_ids}` into the picked labels in option order joined with `"; "` and `{text}` into the trimmed text, so the graph still receives a string and turns, coverage and stop phrases are unchanged; exactly one of the two (both or neither → 422); ids must be known, unique, and one only unless `multi`; free text (object or plain string) is 422 when the question has options and `allow_free_text` is false; the object shape for any other interrupt → 422. Prompt `interviewer.v3.md` (v2 kept). an already answered turn returns its answer without pausing. It does not interrupt when the service refuses (8 asked, or the user answered "That's enough") or another question is open; a message tells the model what to do. `save_interview_turn(topic, question, answer)` records a `noted` turn. `recall_memory()` returns the idea's turns (all runs), covered/skipped/missing topics and questions left. `finish_interview(problem, target_customer, current_alternatives, willingness_to_pay, feasibility)` is the structured output; the node reads its arguments from the loop's messages (none → empty findings). `ended_by` is worked out from the turns, never by the model: `user` (a stop answer in this run), `coverage` (every checklist topic answered or skipped), `cap` (8 asked), else `model`.
- Researcher (SHIP-238, `agent/specialists/researcher.py`, tools in `agent/tools/research_kb.py`, prompt `researcher.v2.md`): at `researching` it first checks the workspace has an Exa key (presence only, `identity.key_readiness`, in a short transaction). With none it does no research: it emits a custom `notice` event `{code: "research.skipped_no_exa", text: "Research is skipped: Exa isn't set up."}`, makes no model or Exa call and no snapshot, sets state `research_skipped` (read with `.get`; `route` then returns `END`, no loop back through the supervisor) and leaves the stage at `researching`; the run ends `succeeded`, and a later run (after the key is saved) starts at `researching`. Otherwise it reads the key in a short transaction, then runs `build_react_specialist` (step limit 80, `finish_tools={finish_research}`) over the `research` chat model, the Exa tools `web_search_exa` / `web_fetch_exa` (`open_exa_tools`, no DB transaction held) and its own tools, seeded with the idea, its `InterviewBrief`, the user's answers and what the run's snapshot already holds. Exa calls are capped at 12 per run (`ExaCallBudget` / `with_call_cap` in `agent/tools/exa.py`; the 13th is not made and the model is told to finish; the count is a Redis counter `agent:exa:{run_id}:calls` (1 h TTL), so every pass and crash re-run of the node shares it). Tools, each in its own short transaction, calling only `research` exports: `kb_lookup(query, k?)` (embeds through `LLMGateway.embed`; embeddings off or failing → name/domain match), `kb_upsert_competitor(name, url, overlap, description?, pricing?)` (upserts by normalized domain, links it to the run's snapshot, returns `{id, name}`), `save_research_item(kind, title, claim, confidence, url?, published_at?, quote?)` (a `competitor`/`market_fact` without a URL or without a `quote`, or any refusal, returns a message to the model, not a failed run), `finish_research(summary, no_direct_competitors, needs_clarification[≤2])` (the structured output). The run's snapshot is opened on demand (`open_snapshot` is idempotent); a node re-run after the snapshot closed (crash before the checkpoint) sees it closed and only moves the run to `scoring`. On finish the node either asks for one clarification round or closes the snapshot (summary ≤ 4,000 characters; when no competitor is linked "No direct competitors found." is added) and moves the run to `scoring`; the runner saves the stage.
- Scorer (SHIP-240, `agent/specialists/scorer.py`, tools in `agent/tools/scoring.py`, scale in `agent/tools/score_scale.py`, prompt `scorer.v2.md`): at `scoring` it runs `build_react_specialist` (step limit 30, `finish_tools={submit_scores}`, `refusals=(ScoreRefused,)`) over the `score` chat model (temperature 0.0), seeded with the idea, its `InterviewBrief`, the user's answers and the latest closed research snapshot (summary, competitors, items with URL and quote; "none was done" with no snapshot). Tools, each in its own short transaction, calling only `scoring`, `research` and `ideas` exports: `get_rubric()` (weights from `scoring.get_rubric` plus the written scale below), `kb_lookup` (the Researcher's tool), `web_search_exa` (search only, `exa_tools_for("scorer")`, capped at 3 per run on its own Redis counter `agent:exa:{run_id}:score_searches`; the 4th is not made and the model is told to submit) and `submit_scores(params[6])`, each `{param, raw, reason, confidence, evidence[{url, title, quote}], no_evidence}` and no total or band. `submit_scores` first checks every evidence URL against the run's `SourceBook` (the snapshot's item and competitor URLs plus the URLs in this run's search results, compared without a `#fragment` or trailing `/`), then calls `scoring.record_score(trigger=manual)`; the module's refusals (`InvalidInputError` with `errors`) and unknown URLs are raised as `ScoreRefused`, which the builder returns to the model as an error result (it never ends the loop). The first refusal lets the model submit again; the second makes the tool answer "Submission is closed" (a success, so the loop ends) and the node fails the run. The Exa key must be saved and have passed its test (`KeyReadiness.READY`); otherwise the loop runs without the search tool and the seed says so. `submit_scores` takes its entries loosely (`list[dict]`) and validates them itself, so a malformed entry is a refusal that counts toward the two. A loop that ends with no stored score fails the run with `score.invalid_submission`; `GraphRecursionError` fails it with `run.step_limit_reached`. A run stores at most one score run: a node entered when `scoring.latest_score` is of this run (crash re-run, or the pass after the Advisor) makes no model call and only routes. Routing: `advising` when the band is `advise` or `promising` and `ADVISED_MARKER` is not yet in `summary`, else `spec_draft` (band `build` always); when the Advisor set `rescore_after` to the newest score run's id, the node scores once more (own search counter `score_searches_rescore`), then clears it; the runner saves the stage. After a successful submission the node emits a custom `score` event `{score_run_id, total, band}` (in `NODE_EVENT_TYPES`) and `node_finished`. Written scale (marks 0–10, integers; between two anchors is allowed): problem_severity 2 nice to have / 5 recurring annoyance, workarounds exist / 8 costly, people already pay or spend time / 10 urgent, frequent, expensive; uniqueness 2 many strong incumbents / 5 crowded with a clear gap / 8 few weak competitors, clear difference / 10 no direct competitor, defensible angle; market_demand 2 no sign / 5 some signals, small market / 8 clear growing demand / 10 large, fast-growing, many paying customers; value 2 marginal / 5 clear but modest / 8 large, users would switch / 10 transformative; feasibility 2 needs tech, approval or capital not at hand / 5 small team with real risk / 8 standard tech, few unknowns / 10 quick with proven tools; timing 2 too early or shrinking / 5 neutral / 8 a clear trend arriving / 10 strong tailwind now.
- Advisor (SHIP-241, `agent/specialists/advisor.py`, tools in `agent/tools/advice.py`, prompt `advisor.v2.md`; the seed pieces it shares with the Scorer are in `agent/specialists/idea_context.py`): at `advising` it reads the idea's newest score run and runs `build_react_specialist` (step limit 40, `finish_tools={finish_advice}`, `refusals=(AdviceRefused,)`) on the `advise` chat model (temperature 0.5). The seed has the idea, interview, research, the score per parameter (reason, sources) and the weakest parameters computed in code (points lost `weight × (10 − raw)`, ties to the heavier weight; 3 for `advise`, 2 for `promising`). Tools: `kb_lookup`, `web_search_exa` (search only, 3 per run on counter `advise_searches`), `save_suggestion` (a `NewSuggestion`; refused past the maximum (5, or 2 for `promising`), when it targets none of the weakest parameters, or when an evidence URL is not a source from the snapshot, the score's evidence or this run's searches) and `finish_advice` (refused below the minimum, 3 for `advise`, 0 for `promising`; the second refusal closes it and the node fails the run with `advice.invalid_submission`; a loop that ends short does the same; `GraphRecursionError` fails it with `run.step_limit_reached`). Without a usable Exa key it goes without the search tool. With no score, or a `build` score, the node only moves on to `spec_draft`. A `promising` idea goes to `spec_draft` with no interrupt. An `advise` idea pauses on `advice_decision`: `continue` → `spec_draft`; `stop` → `advice_stopped` (the supervisor ends the run `succeeded`, the idea stays at `advising`); `revise` → `ideas.apply_revision` with `revised_text` plus, when any were accepted and the text still fits in 10,000 characters, a block `Accepted improvements:` with `- title: rationale` per accepted suggestion (otherwise a `notice` `advice.notes_dropped`), accepted suggestions get status `accepted` (ids not of this score run are ignored), state `rescore_after` = the advised score run's id and stage `scoring`. The Scorer then scores again once and the run goes to `spec_draft`: one Advisor pass per run. Re-run safety: with enough suggestions saved for the score the node makes no model call, so the crash re-run and the re-run after the interrupt add nothing, and the revision write repeats harmlessly. State fields `rescore_after` and `advice_stopped` are read with `.get`. The web answers it with `AdviceDecision` (SHIP-245) through `POST /v1/runs/{id}/resume`.
- Architect (SHIP-244, `agent/specialists/architect.py`, tool in `agent/tools/spec.py`, prompt `architect.v2.md`): at `spec_draft` it runs `build_react_specialist` (step limit 15, `finish_tools={save_spec}`, `refusals=(SpecRefused,)`) on the `spec` chat model (temperature 0.2), seeded with the idea, interview, research, the score and the suggestions the user accepted. `save_spec(kind, problem, target_users, solution, key_features, non_goals, competitive_edge, success_metrics, risks, open_questions)` refuses an empty section, a `kind` that is not `software`/`other` or a spec over 50,000 characters; the first refusal lets the model try again, the second closes it and the node fails the run with `spec.invalid_submission` (also when the loop ends with no spec; `GraphRecursionError` → `run.step_limit_reached`). A valid spec is rendered and saved as the next version (`source agent`, this run's id) and sets `ideas.kind` only when it was null. The node then calls `interrupt({"type": "spec_review", "spec_version_id", "number", "kind"})` (the latest version) and, once resumed with `{"confirmed_number": n}`, sets stage `spec_confirmed` (the confirm route already moved the idea, so the stage sync writes nothing). When the idea already has a spec (a crash re-run, the re-run after the interrupt, or an earlier run's draft) the node makes no model call and goes straight to the review. The user edits and confirms through the spec routes (see Specs); the run route refuses to resume a `spec_review` interrupt.
- Planner (SHIP-246, `agent/specialists/planner.py`, tools in `agent/tools/planning.py`, prompt `planner.v2.md`): `spec_confirmed` runs `build_react_specialist` (step limit 20, `finish_tools={save_plan}`, `refusals=(PlanRefused,)`) on the `plan` chat model, seeded with the idea, interview, research and the confirmed spec. `propose_phases(phases)` (3–7 phases `{name, goal, exit_criteria}`, else a refusal with no pause) calls `interrupt` `phase_review`; the user's reviewed list (`PhaseReviewResume`) is the only phase list the plan may use and is returned to the model numbered from 0. `save_plan(tasks)` (`{key, phase, title, description, estimate, labels, blocked_by, parent_key?}`) builds a `planning.PlanInput` from the reviewed phases and saves a **draft** plan for the confirmed spec version through `planning.save_plan`; an `InvalidPlanError` (cycle, estimate above 8 or not Fibonacci with a split hint, unknown task or phase, and so on) or a malformed task comes back to the model naming the tasks; first refusal lets the model try again, the second closes the tool and the node fails the run `plan.invalid_submission` (also when the loop ends with no plan; `GraphRecursionError` → `run.step_limit_reached`). No confirmed spec → `spec.not_found`. When the plan for the spec version already exists the node makes no model call; a resume continues the loop from its checkpoint, so the phase proposal is not repeated. Success sets stage `planning`; marking the plan `ready` is not done here.
- Interleaving (SHIP-238): state fields `clarification` (pending questions) and `clarification_rounds` (0 or 1) (read with `.get`; old checkpoints lack them). `finish_research` with questions and `clarification_rounds == 0` sets `clarification` (≤ 2) and leaves the stage `researching` with the snapshot open; with `clarification_rounds == 1` the questions are ignored. `route` sends the run to the Interviewer while `clarification` is non-empty, whatever the stage. The Interviewer then asks the first question as a turn (topic `other`, through `ideas.open_question`, so it counts toward the 8-question cap and a refused one is dropped), no model call, with the usual `interrupt({"type": "question", "question"})`, and keeps the rest in `clarification` for its next visit; the stage then routes back to the Researcher, which runs again on the same snapshot.
- Tool-calling specialists are built with `build_react_specialist(prompt, tools, model, step_limit, finish_tools=(), refusals=())` (`agent/specialists/base.py`): model reply → tool calls → reply, ending when a reply asks for no tool or right after a `finish_tools` tool succeeds; the step limit is the subgraph's recursion limit, per invocation.
- Checkpointer (`agent/checkpoint.py`): `AsyncPostgresSaver` on its own `psycopg` pool, search path `agent` (migration `0012_agent_checkpoints` creates the schema and lets `metis_app` create and use tables in it; the library's `setup()` creates the tables, run at agent-worker start by `agent_on_startup`). No RLS: a thread id is a run id and only workers read them.
- Prompts: `server/metis/prompts/<specialist>.v<N>.md`, loaded by `agent/prompts.py` `load_prompt(name, version=None)` (latest by default; `PromptNotFoundError` for an unknown name or version). New wording is a new version file.
- Running a run (SHIP-228): job `run_graph(ctx, *, run_id, workspace_id, resume=None)` in `jobs/run_graph.py`, a thin wrapper over `agent/runner.py` `execute_run`. The workspace id is an argument because RLS hides the run row until the session knows its workspace; enqueue with keyword arguments (`enqueue("run_graph", run_id=…, workspace_id=…, resume=…)`) so `logged_job` binds them. `ctx["run_deps"]` (`RunnerDeps`: sessions, checkpoint database URL, optional specialist overrides, optional LLM HTTP client factory) replaces the defaults; tests use it. Each run gets one `LLMGateway` (closed when the stream ends); the default nodes are the real Interviewer, Researcher, Scorer, Advisor and Architect and stubs for the rest (all stubs with `AGENT_STUB_SPECIALISTS`), and overrides win. Steps:
  - **Lock** (`agent/run_lock.py`, keys in `core/run_control.py`): Redis `lock:run:{run_id}`, `SET NX` with an owner token, TTL `RUN_LOCK_TTL_SECONDS` (60) kept alive by a heartbeat every `RUN_LOCK_HEARTBEAT_SECONDS` (20), released only by its owner. Held by another worker → the job exits (`run.lock_held`). If the key is taken over, the run stops without touching its row (`run.lock_lost`).
  - **Which run**: terminal → ignored; `resume` given and the run not `awaiting_user` → ignored; `awaiting_user` without `resume` → ignored; unknown run → ignored. `cancel:{run_id}` set before the start → `cancelled`.
  - **Input**: `resume` → `Command(resume=…)`; else a checkpoint exists (crash recovery) → `None`, continuing from it; else a new run: `initial_state` from the idea's stage and `max_steps` from `identity.get_settings_overview`. The run moves to `running` and `run_status: running` is published first. Checkpoints are written with `durability="sync"`, so no completed step is lost. No transaction is open while the graph runs; every status change is its own committed transaction, and events are published after the commit.
  - **Stream** `astream(stream_mode=["updates","messages","custom","tasks"], subgraphs=True)` → events (`agent/run_events.py`); a specialist's own tool loop is a subgraph, and only its `messages` chunks are published (its inner tasks and updates are skipped), named after the top-level node (from `langgraph_checkpoint_ns`). A specialist task start → `node_started {node}` (the supervisor publishes nothing); a node's custom `node_finished` / `tool_call` / `notice` pass through (`notice` data is `{code, text}`; it is on the stream, so a replay shows it again); model text → `token {node, text}`, buffered and flushed about every 100 ms and always before the next event; a model's tool call → `tool_call {node, name}` (never the arguments); `__interrupt__` → stored and published as `interrupt` (the payload) then `run_status: awaiting_user`; `run_status {status, error?}` for every status.
  - **End**: no `last_error` → `succeeded`; `last_error` set (the step limit) → `failed` with that code; any exception → `failed` with its `MetisError` code, else `run.failed`; the stored `{code, message}` message is the catalog title, never the exception text (logged server-side). `asyncio.CancelledError` (worker shutdown) is not caught: the run stays `running` for recovery. The terminal `run_status` starts the stream's 24 h TTL. `cancel:{run_id}` is checked after every step (`updates` chunk): set → `cancelled`, the checkpoint stays; it takes effect at a step boundary.
  - **Stage sync** (`agent/stage_sync.py`): after each top-level `updates` chunk the runner copies every `stage` a node set to `ideas.stage` (`ideas.transition`, own short transaction; a stage the idea already has is not written again, so a node re-run after a crash is safe). When a run starts or resumes, the checkpoint's stage is saved the same way first, which closes the gap where a crash came after a node's checkpoint but before its write. A move the transition table refuses fails the run with `idea.invalid_transition`. Nodes never write `ideas.stage` themselves.
  - **Start gate**: `ideas.start_run` refuses with `LlmNotReadyError` unless the workspace's `llm` key row has `last_test_ok is True` (`identity.key_readiness` → `KeyReadiness`: `ready`, `not_configured`, `not_tested`, `test_failed`). It reads the row only, and runs after the idea and idempotency lookups, so a repeated start with the same key still returns its run.
  - **Crash recovery** (`agent/recovery.py`, run by `agent_on_startup`): every `running` run whose lock is gone is enqueued as `run_graph` under the job id `{run_id}:recover:{unix seconds}` (the run's first job id is still remembered by Arq and would be dropped); the job continues from the last checkpoint. A failed scan is logged (`run.recovery_failed`) and never stops the worker. Only startup runs it today; the scheduler does not sweep.

## API Conventions

| Concern     | Rule                                                                            |
| ----------- | ------------------------------------------------------------------------------- |
| Prefix      | `/v1`                                                                           |

## Jobs and Events

| Queue         | Jobs                                          | Notes                    |
| ------------- | --------------------------------------------- | ------------------------ |
| `agent`       | `run_graph(run_id, workspace_id, resume?)`    | one per run (Redis lock) |
| `watch`       | `run_graph` with `stage=watch`                | keyed `idea_id:date`     |
| `maintenance` | `outbox_relay`, `distill_guidance`, `cleanup` | single concurrency (`max_jobs=1`), own worker process |

Enqueue only through `core.jobs.enqueue(job_name, *args, job_id=...)`; a job must be listed in `JOB_QUEUES`. The same `job_id` enqueues once. Job functions use `@logged_job` (binds `job_id`, `run_id`, `workspace_id`). The `watch` queue lands with market-watch. Scheduler is an Arq cron worker whose jobs only enqueue (`outbox_relay` every 5 s, `cleanup` nightly 03:00 UTC).

Run events go through `core.events`: `publish(run_id, type, data)` appends to the Redis stream `run:{run_id}` (`MAXLEN ~ 5000`); `read(run_id, after_id, block_ms)` does one `XREAD` and yields `RunEvent{id, run_id, type, data, ts}`. The Redis entry id is the SSE event id (`Last-Event-ID`). Publishing a terminal `run_status` (`succeeded`, `failed`, `cancelled`) sets a 24 h TTL on the stream.

The SSE route (`modules/ideas/controller/run_events.py`, frames in `helpers/sse.py`) checks the run (404 `run.not_found`) and frees its DB session before streaming. Frames: `id: <redis id>`, `event: <type>`, `data: <RunEvent JSON>`; `retry: 3000` first; `: ping` after each 15 s read with no event; the stream ends after a terminal `run_status`. A finished run is read once without waiting; if its stream has expired it gets one `run_status` frame (no `id`) from the database. An undecodable entry sends `event: error` (`run.event_malformed`) and closes. Bad `Last-Event-ID` / `after` → 422. The stream uses its own Redis client (the shared one has a 0.5 s socket timeout).

Domain events (`DomainEventType`) go through `core.outbox`: a service calls `add_event(session, DomainEvent(...))` inside its own transaction (it only inserts; the caller commits), so a rolled-back change leaves no event. Handlers subscribe with `@on_event(DomainEventType.X)` and receive the `DomainEvent`; they open their own sessions and use other modules only via `service.py`. The `outbox_relay` job runs `relay_once`: up to 100 unpublished events, oldest first, `FOR UPDATE SKIP LOCKED` so concurrent relays never share an event; success sets `published_at`, a handler error increments `attempts` and retries the whole event on the next run; after 10 attempts the event stops and `outbox.event_dead` is logged. Delivery is at least once, so handlers must be idempotent, keyed on `event.id` (UUIDv7 from `core.ids.uuid7`). `core.outbox` has no RLS (the relay reads across workspaces).
